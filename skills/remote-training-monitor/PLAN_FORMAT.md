# Run Plan Format

One directory per Target Key holds the human-facing Run Plan and the
machine-facing state. Project-wide files sit beside them:

```text
<project-dir>/.remote-monitor/
├── adapter.md            # project adapter: exact commands and sources, written once (optional)
├── BOARD.md              # generated by the board route; never edited by hand
└── <target-key>/
    ├── plan.md           # Run Plan: Phases, Monitoring Contract, Approvals, History
    └── state.json        # the fields a wake reads before observing; shape in ../state.schema.json
```

`plan.md` is read by people and rewritten only in the ways listed under
Mutation. `state.json` is what `iterate` parses, so a wake never has to find a
cursor inside prose; it is validated with `scripts/validate_state.py` after
every read and before every write.

## Target Key

The Target Key identifies the monitored workflow, not its current attempt.
For an already running job, derive it from the control-plane scope and initial
immutable job identity, for example `slurm-cluster-a-4821`. For a pipeline
not yet launched, generate a unique local run ID. Use a filesystem-safe key.
Once written, the key and state directory remain stable across phases and
retries.

Record each phase launch or retry with a distinct `attempt_id`, exact remote
identity and artifact paths in History; retain prior failure evidence. Update
`current_attempt` and reset observation cursors for the new attempt. Keep
retry counts across attempts. An unrelated workflow gets its own key.
Existing plans retain their original keys; do not rename them to match these
examples or overwrite an existing directory for a similarly named job.

## Repo hygiene

On first write, if the project is a git repository, append `.remote-monitor/`
to the exclude file resolved by `git rev-parse --git-path info/exclude` when
it is not already ignored. That keeps the directory out of commits without
editing any tracked file. After a terminal state the directory is kept and
named in the report.

## Project adapter

Many projects already know how to launch, approve, observe and record a run.
`adapter.md` caches that once so every plan and wake reuses it instead of
rediscovering it. Write it during the first `plan` in a project when Discovery
finds any of these; leave a heading out when the project has none:

```markdown
# Project adapter

- Control plane: slurm over `ssh <host>`; account `<user>`; partitions `<...>`
- Observe: `squeue -j <id> -h -o '%T %M %R'` · `sacct -j <id> -X -n -o State,ExitCode,Elapsed,NodeList` · `scontrol show job <id>`
- Logs: StdOut/StdErr from `scontrol`; bounded `tail -n 200`
- Progress: `<output dir>/run/run.json` (`status.stage`) · W&B run `<project>/<run>` (`train/*` per step) · `checkpoint-*/` mtimes
- Exit checks source: `evidence/docs/<packet>/<PACKET>.json` → `packet_body.exit_checks`
- Approval source: the frozen packet above; the user replies with its SHA-256 in chat; recorded in `approval-log.json`
- History file: `evidence/docs/<packet>/RUN_STATE.md` (one per run; the plan's History lives there)
- Planned source: `plans/<PLAN>.md` (runs not yet planned by the skill, for the board)
- After a run: `python3 scripts/runs.py pull` then `runs.py check`
- Timezone for reports: `America/New_York`, shown beside UTC
```

The adapter is read-only toward the project: it names files and commands, it
never changes them. `.remote-monitor/adapter.md` is kept out of git with the
rest of the directory; a project that wants it tracked copies it elsewhere and
points the plan at the copy.

## Discovery and approval

Inspect launch scripts, job specs, configs, working directories, checkpoints
and bounded logs read-only. Draft phases from the evidence; use one phase
named `run` when there is no multi-phase workflow. Ask only for missing
information needed to identify the target, define success or establish
authority. Use `PLAN_EXAMPLES.md` when an example would clarify the format.

**Exit checks are copied, never pointed at.** When the project has an
approval artifact that lists them (a frozen packet, a spec), the Phases table
carries every check verbatim, one per line, with the artifact's path and hash
beside the table. A plan whose exit checks read "see packet" cannot answer
"what are we checking for" and is not a Run Plan.

**Approval source.** When the project approves work with its own artifact, the
plan's Approvals section records that artifact's path, its hash and the user's
words that matched it. The skill asks for no second approval of the same
scope. Without such an artifact the plan itself is what the user approves.

- `plan` writes and presents the plan without scheduling or launching. The
  run state is `PLANNED`, the monitor `OFF (draft)`.
- `start` with `observe_only` and no launch action proceeds after presenting
  the plan; it does not require another approval.
- A launch or `auto_low_risk` policy requires matching approval of the
  concrete plan. Record already supplied approval when it covers that exact
  scope; otherwise present the plan and wait with the monitor `WAITING`.
  Approval covers phase 1's named launch and the stated recovery envelope.
  Later phases gate individually.
- Changes to phase semantics, resources or recovery policy bump the revision
  and invalidate standing approvals.

```markdown
---
target_key: slurm-4821
run_name: fine-tune 7B on mix-v3
harness: claude-code | codex-desktop | codex-cli
control_plane: slurm | kubernetes | docker | systemd | managed | process | custom
project_dir: /abs/path
adapter: .remote-monitor/adapter.md      # omit when there is none
wake_mode: COMPLETION | INTERVAL
recovery_policy: observe_only | auto_low_risk
approval_source: evidence/docs/<packet>/<PACKET>.json sha256 <hash>   # omit when the plan itself is approved
history: evidence/docs/<packet>/RUN_STATE.md    # omit when History lives below

plan_revision: 1

## Monitoring Contract

- Target identities: job id, attempt, owner, working directory on the host
- Adapter and exact observation commands (or "per adapter.md")
- Training signals measured, their sources, and any threshold that differs
  from the defaults in `ADAPTERS.md`
- Success, failure and intentional-stop evidence
- Wake Mode and its basis: the waiter's exit conditions and backstop, or the
  Cadence (estimated remaining time, stability)
- Recovery policy, retry budget, rollback point requirements
- Approval source and approval holder
- Resource, cost, storage, publication and destructive-action limits
- Discovery gaps: what could not be found and what the user supplied
```

A phase whose launch action is "already running" has no gate before it. A
phase with a real launch action gates on Approval.

When `history` names a project file, the skill appends its History lines
there, in that file's existing style (a dated heading per event is fine), and
plan.md's History section holds only the pointer. One timeline per run.

## state.json

The shape is `state.schema.json`; this is one instance:

```json
{
  "target_key": "slurm-4821",
  "run_name": "fine-tune 7B on mix-v3",
  "plan_revision": 1,
  "run_state": "RUNNING",
  "since": "2026-09-04T12:30:00Z",
  "health": "FINE",
  "monitor": { "state": "WATCHING", "reason": null },
  "heartbeat": { "harness": "claude-code", "mode": "completion", "id": "bg-7f2c", "deadline": "2026-09-04T16:30:00Z", "interval_min": null, "cadence": null, "durability": "session-bound", "project_dir": "/abs/path" },
  "current_phase": 1,
  "current_attempt": { "attempt_id": "phase-1-attempt-1", "control_plane": "slurm", "scope": "cluster-a", "job_id": "4821" },
  "progress": { "step": 12400, "total_steps": 20000, "rate": "1.9 step/s", "eta": "2026-09-04T13:40Z", "last_checkpoint": "ckpt/step-12000", "stage": null },
  "checks": { "passed": 0, "total": 3 },
  "cursor": { "log_offset": 48213, "scheduler_seen": "RUNNING 01:12:04 gpu-a100" },
  "next_action": "exit checks on completion",
  "last_observed": "2026-09-04T12:30:00Z",
  "estimated_remaining_min": 70,
  "retries": {}
}
```

- `since` is when `run_state` last changed; `last_observed` is the last
  Observation. The board and the STATE line use `since`.
- `heartbeat.id` is the id alone. What replaced what, and why, is a History
  line. An `interval` heartbeat has `interval_min` and `cadence`; a
  `completion` heartbeat has `deadline`.
- Before scheduling, `heartbeat` is `null` and the monitor is `OFF (draft)`.
  Before first launch, `current_attempt`, `since`, `health` and
  `last_observed` may be `null`.
- `health` is `null` unless `run_state` is `RUNNING`.
- `progress`, `checks` and `next_action` are written on every wake. They are
  what the board shows; a wake that leaves them stale leaves the board stale.

Run `python3 <skill-dir>/scripts/validate_state.py <path>` after reading the
file and before writing it. A rejected read is reported as the first line of
the wake and ends the iteration before any Observation; a rejected write is a
bug in the wake, fixed before the file is saved.

## Mutation

- The skill appends to Approvals and History and updates `current_phase`,
  the heartbeat, and the state fields.
- Phase semantics, resource envelope and recovery policy change only by
  bumping `plan_revision`, which voids every standing Approval. The Gate
  Packet hash rule in Phase Gate is this rule applied per phase.
- A wake never edits Phases and never re-plans. A missing `plan.md` is a
  one-line refusal naming the expected path and directory.
- Approvals are recorded as the user's words plus the phase name, revision or
  artifact hash they match. "Looks good" against revision 2 is not an
  approval of revision 3.
